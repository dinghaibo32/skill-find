# 中文提交信息规范

## 概述

基于实际 diff 生成约定式提交（Conventional Commits）风格的中文提交信息。核心原则：信息描述"为什么改"而非罗列文件；一次提交只讲一件事。

## 使用步骤

1. **读改动**：运行 `git status` 与 `git diff --staged`（未暂存则 `git diff`）。只依据真实 diff 撰写，不凭记忆编造改动内容。
2. **判断是否拆分**：若暂存区混有多个不相关改动（如功能 + 无关格式化），建议用户按主题拆分提交，分别撰写信息。
3. **选类型**：

   | 类型 | 适用 |
   |------|------|
   | feat | 新功能 |
   | fix | 缺陷修复 |
   | refactor | 不改行为的重构 |
   | docs | 仅文档 |
   | test | 仅测试 |
   | chore | 构建/依赖/杂项 |

4. **按格式撰写**：

   ```text
   <类型>(<scope>): <一句中文摘要，不超过 50 字，不加句号>

   <正文：为什么改、关键决策、影响范围；每行不超过 72 字>

   <可选脚注：BREAKING CHANGE: ... 或 Closes #123>
   ```

   - scope 用模块名（如 `llm`、`frontend`），跨模块可省略；
   - 摘要说清"做了什么 + 为了什么"，例：`feat(llm): 新增单次调用 token 费用统计`；
   - 破坏性变更必须在脚注写 `BREAKING CHANGE:` 并说明迁移方式。
5. **确认后提交**：把信息展示给用户确认；仅在用户明确要求提交时才执行 `git commit`，不得主动提交。

## 常见错误

| 错误 | 修正 |
|------|------|
| "更新代码"、"修改若干问题" | 摘要必须具体到改动主题 |
| 罗列改动文件名当正文 | 正文写动机与影响，不写文件清单 |
| 一个提交塞多个主题 | 先拆分再分别撰写 |
